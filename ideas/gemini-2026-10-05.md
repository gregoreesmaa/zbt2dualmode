Why It Fails in Real-World Deployments
While compiling the RCP firmware and running cpcd is relatively straightforward for an experienced developer, dynamic multi-protocol on a single radio comes with deep protocol-level compromises:

Channel Mismatch & Blind Time: Both networks must operate on the exact same 2.4 GHz IEEE 802.15.4 channel. If they differ, the radio must rapidly retune its frequency, leaving gaps where incoming packets for the idle protocol are completely dropped.

Lack of ACKs and Route Breakage: Zigbee and Thread both rely heavily on timing-critical ACKs. When the radio is busy receiving a long Thread/Matter frame, it misses Zigbee ACKs. In Zigbee, missed ACKs make routers assume a neighbor link is dead, triggering frantic route recalculations (route storms) that degrade the mesh.

Firmware Arbitration Latency: Silicon Labs’ internal radio arbiter must arbitrate priority between Zigbee frames and Thread frames. Because neither protocol was designed with time-sharing in mind, buffers overrun under moderate home automation load.

Practical Recommendation
If your goal is to tinker with embedded systems, explore Simplicity Studio, or write a tailored radio scheduler, the ZBT-2 is an accessible development target.

However, if your goal is a production-grade smart home, running two distinct physical coordinators (e.g., the ZBT-2 dedicated to Zigbee and a second dongle or existing border router dedicated to Thread) provides far greater reliability and network health.

From an engineering standpoint, dynamic multiprotocol (DMP) fails because the physical radio tries to pretend it is two independent transceivers while both protocol stacks remain completely oblivious to the hardware constraints.

To make concurrent Zigbee and Thread work reliably on a single Silicon Labs MG24, you have to break abstraction layers and tackle three core problems: time-sharing, packet dropping / ACK failure, and channel collision.

Here are the clever architectural and firmware-level ways an engineer can approach this:

1. Unified Channel Pinning (Eliminating the Frequency Hop)
The most fatal source of dropped packets is retuning the radio synthesizer between two different IEEE 802.15.4 channels. Synthesizer lock time introduces deaf periods, and incoming packets on Channel B while listening on Channel A are permanently lost.

The Hack: Hard-bind both protocols to the exact same physical channel (e.g., Channel 25).

Why it works: The MG24’s baseband demodulator can receive any valid IEEE 802.15.4 frame on that frequency without retuning.

Firmware implementation: Instead of letting the stacks manage radio state independently, configure RAIL to keep the receiver open in promiscuous / multi-PAN mode.

The EFR32MG24 hardware supports Hardware Multi-PAN Filtering (up to 3 PAN IDs concurrently in silicon).

The hardware MAC filter inspects the PAN ID in the frame header on the fly. If it matches PAN A, it routes the buffer to the Zigbee queue; if PAN B, to the Thread queue. The radio never switches frequencies or deafens itself.

2. Microsecond-Level Custom Radio Arbiter
Silicon Labs provides a default priority scheduler in RAIL, but it uses static priority classes (e.g., Thread high-priority TX beats Zigbee low-priority RX). This is too blunt and causes Zigbee route storms.

Context-Aware Arbitration: Rewrite the RAIL arbiter hooks to inspect packet semantics before granting the radio:

Protect ACK Windows at All Costs: In 802.15.4, an ACK must be returned within a strict window (typically 192–864 microseconds after frame reception). Your arbiter should register an uninterruptible "ACK pending" state immediately after a successful frame reception, locking out the other stack from initiating a transmission for ~1 ms.

Differentiate Control vs. Data: Route maintenance frames (Zigbee Link Status, Thread MLE Advertisements) and pairing handshakes should be elevated above bulk telemetry (e.g., temperature sensor reports or power meter bursts).

Jitter & Backoff Injection: If the Thread stack requests a TX while Zigbee is awaiting an ACK, the firmware shouldn't simply fail the Thread TX; it should dynamically manipulate the CSMA-CA backoff exponent (BE) to postpone the Thread transmission cleanly into the next contention period.

3. Exploiting Dual SoCs: Offloading the Stacks
The ZBT-2 has two processing units: an ESP32-S3 and an EFR32MG24. In the standard Home Assistant design, the MG24 runs the entire RCP/NCP, and the ESP32 acts merely as a dumb USB-to-UART bridge.

The Split-Core Co-Processor Model:

Keep the MG24 strictly as an ultra-lean RAIL raw-frame transceiver / hardware arbiter.

Move the Upper MAC and protocol framing layers (zigbeed and otbr-agent) off the host machine and run them directly on the ESP32-S3's dual 240 MHz Xtensa cores.

Why this helps: A host OS running Linux introduces USB scheduling latency, OS context-switch overhead, and daemon socket delays via cpcd. Handling time-critical MAC coordination and backoff decisions between Zigbee and Thread over high-speed local SPI/UART between the ESP32 and MG24 drops latency from milliseconds to microseconds.

4. "Zigbee Sleepy Router" / Asymmetric Role Trick
If one of the two networks doesn't need to be a full-fledged mesh coordinator with heavy routing duties, you can redesign its role:

Thread as the Primary Mesh: Configure the Thread side as the true Full Thread Device (FTD) / Border Router, handling constant routing.

Zigbee as an End-Device Bridge / Fast-Poller: If you only have a few Zigbee devices or your Zigbee network has stable mains-powered routers nearby, you can tune the coordinator's communication window:

Force Zigbee non-critical messages to buffer upstream.

Use scheduled time-division multiplexing (TDM) aligned with beacon intervals or predictable poll cycles, granting Thread 80% duty cycle and Zigbee 20% in clean, uninterrupted bursts.
